# ADR-010: Data model conventions — identifiers, units, versions, catalogues, deletion

**Status:** Proposed
**Date:** 2026-11-17
**Deciders:** the owner
**Draft:** §2.1–§2.5c, §6, §9.3, §9.5 · **Related:** ADR-002, ADR-009, ADR-011, ADR-012, ADR-020

**In plain words:** the house rules for how every table in v3 is shaped, so that all modules look
alike, an office can be moved between servers, and old approved work can always be read exactly as
it was approved.

## Context

- Draft constraints: globally unique identifiers; export/import of one office; units pinned to a
  catalogue version and to a workflow definition version; revisions frozen at approval; nothing
  removed by itself except deleted items after 30 days; times stored once in UTC.
- Today: MongoDB ObjectIds, `updatedAt` used as the version of a record, a separate revision
  counter per table for Tools 3–5, hard deletes with a cascade written by hand.

## Decision

### Identifiers

- Primary keys are **UUID version 7** (time-ordered, generated by the database). They are unique
  across installations, which is what makes the office export/import a copy rather than a
  renumbering, and they index well.
- **Human codes are separate columns:** office code (`SY`), unit code (`ESMS-SY-024`,
  `ESMS-SY-024-A03`) from a per-office counter; old codes are kept as aliases (draft §2.5c).
- Rows migrated from v2.5 get **deterministic** UUIDs derived from their old identifier, and keep
  the old one in a `legacy_id` column (ADR-020).

### Structure

- **One database schema per module** (`identity`, `access`, `org`, `workflow`, `screening`, …).
  Ownership is visible in the name and can be granted per schema.
- **Foreign keys everywhere, including across modules to kernel tables** (`unit_id`, `person_id`,
  `org_unit_id`, `catalogue_version_id`). A module still never *queries* another module's tables
  (ADR-001); the key only guarantees the row it points to exists.
- **`org_units`** holds the tree (`id`, `parent_id`, `kind`, `code`, `name`) with its closure
  table (ADR-009). **`units`** holds the workflow units, each owned by one org unit (a project or
  an activity) and pinned to a `workflow_definition_version` and a `catalogue_set_version`.
- Every table of office data carries `office_id` (ADR-009), set by the database from its unit.
- **Tool data lives in typed tables** (real columns, constraints, indexes), pointing to `unit_id`.
  Not a generic "form answers" table: the tools have rules, totals and reports that typed columns
  serve and a generic store would hide.

### Versions and concurrent edits

- Every editable aggregate (a unit's facts, a step of a tool, a table of rows) has an integer
  **`version`** column, raised by one on each save in the same statement that checks it. This
  replaces both of today's mechanisms (the `updatedAt` trick and the per-table revision counter)
  with one, and keeps the `409 STALE_VERSION` behaviour (D62).

### Catalogues and translations (draft §2.4)

- `catalogue` → `catalogue_version` (draft or published, immutable once published) →
  `catalogue_item` (stable key, order, retired flag) → `catalogue_item_text` (item, language,
  text). A unit references items by stable key **within its pinned version**.
- Interface languages are data (`languages`); a missing translation falls back to English at read
  time. Text typed by people is stored once, in the language typed, with its direction detected.

### Deletion

- **Soft delete** for what the draft sends to Deleted items (units, files, library documents): a
  `deleted_at` and `deleted_by`; default queries exclude them through a view per table, so a
  forgotten filter cannot show a deleted row.
- **Purge** after 30 days is a worker job that calls each module's lifecycle hook (ADR-012) inside
  one transaction per unit; the history keeps the record that it happened.
- People, offices, roles, catalogue items and history are never deleted (deactivated, closed,
  retired).

### Time

- `timestamptz` in UTC everywhere; each office has a time zone used for its exports and for "which
  year does this belong to" (draft T1, T2). Dates without a time (project start, end) are `date`.

### Flexible data

- JSON columns only where the shape is truly open or frozen: revision snapshots (ADR-011),
  workflow definitions (ADR-012), history values, integration payloads. Never for data that is
  filtered, joined or reported on.

## Options considered

| Topic | Chosen | Alternatives | Why |
|---|---|---|---|
| Identifiers | UUID v7 | Sequences (collide between installations); random UUID v4 (scatters indexes); prefixed text ids | Office export/import needs global uniqueness; v7 keeps inserts ordered. |
| Tree | Parent column + closure table | Path column (`ltree`, PostgreSQL only); recursive queries each time | Fast at any depth, portable (ADR-002). |
| Tool data | Typed tables per tool | One generic answers table; documents in JSON | Constraints, totals and reports need real columns. |
| Version | Integer per aggregate | Timestamp as version (today); row hash | One mechanism, no clock dependence. |
| Deletion | Soft delete + view + purge job | Hard delete with a hand-written cascade (today) | Deleted items for 30 days; no forgotten cascade. |
| Module data | Schema per module | One schema with prefixes | Ownership and grants visible in the database. |

## Consequences

- Easier: an office is a closed set of rows that can be exported and imported; old revisions read
  the catalogue texts they were approved with; a new module follows a fixed shape.
- Harder: catalogue lookups always go through the pinned version; soft-deleted rows must be
  excluded from unique constraints (partial indexes); UUIDs are less readable than numbers in
  support work (the human codes are for that).
- To revisit: nothing foreseen.
