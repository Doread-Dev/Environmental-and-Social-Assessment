# CLAUDE.md

This file provides guidance to Claude Code when working in this repository.

## What this is

ESMS (Environmental and Social Management System) — a workflow app for environmental & social due diligence of development projects (AKF Syria branding in exports). Two independent apps in one repo, each with its own `package.json`; there is no root package or workspace tooling:

- `backend/` — Node.js + Express 4 + Mongoose 8 (CommonJS), JWT auth, Joi validation. REST API under `/api/v1`.
- `frontend/` — React 19 + Vite 7 + React Router 7 + Tailwind CSS 4 (ES modules, plain JSX — no TypeScript). Deployed to Vercel.

The domain workflow is strictly ordered, and most code is organized around it:
**Screening (Tool 1) → Assessment (Tool 2) → SEMP: Management Activities (Tool 3) + Mitigation Plan (Tool 4) → Monitoring (Tool 5)**, plus Annex and Settings.

## Commands

Backend (`cd backend`):

- `npm start` — production start.
- `npm run seed` — upserts the 4 lookup collections (impact categories, impact questions, indicators, job titles) by a stable key (category `code`, question text, indicator name, job title name). Safe to re-run: existing rows keep their `_id`, so scores, monitoring records and users stay linked. Does not delete rows that are no longer in the seed, and does not create users.
- `SEED_EMAIL=... SEED_PASSWORD=... [DEMO_PASSWORD=...] node scripts/seed-demo-project.js` — through the real API (needs an **admin** login; use the `DEV_ADMIN_*` values from `backend/.env`): creates or resets one demo user per role, `demo.<role>@example.com` (admin endpoints, then signs in as each to swap the temporary password for `DEMO_PASSWORD`, default `SEED_PASSWORD`), then (re)creates `[DEMO] Al-Salam Water Network Rehabilitation`, a project that has passed all 5 tools, using the submit/approve endpoints. It also uploads one generated sample PDF to the library, `[DEMO] Sample guidance`, linked to Tool 4 (`mitigation`), never a client file. It first deletes every previous demo project copy (by title, archived ones too) and the previous demo library document straight in MongoDB (no log entry), so only one of each stays; refuses to run when `NODE_ENV=production`. Never prints passwords.
- `node scripts/create-admin.js` — creates an admin (the only way to create the first user). Asks for name/email/password, or reads `ADMIN_NAME` / `ADMIN_EMAIL` / `ADMIN_PASSWORD`. Never prints the password; fails if the email exists. No forced change at first login (the operator chose the password).
- `node scripts/reset-password.js [--activate]` — break-glass reset of any account's password, straight in MongoDB (asks, or `RESET_EMAIL` / `RESET_PASSWORD`). `--activate` also reactivates a deactivated account. Clears a pending forced password change.
- `node scripts/clean-test-data.js` — deletes ALL domain data (projects, screenings, assessments, management activities, mitigation plans, monitoring). Destructive; ask before running. Refuses to run when `NODE_ENV=production`.
- `npm test` (`npm run test:watch`, `npm run test:coverage`) — Vitest + Supertest, see "Tests" below. Needs MongoDB running.
- `npm run lint` / `npm run lint:fix` — ESLint flat config (CommonJS, Node globals, `eslint-config-prettier`).
- `npm run format` / `npm run format:check` — Prettier, backend style: double quotes, semicolons, width 100.

## Backend architecture

Request pipeline (`src/app.js`): `trust proxy` from `TRUST_PROXY` → helmet → cors → body parsers (10mb) → morgan (off when `NODE_ENV=test`) → `GET /health` → `app.use('/api/v1', apiLimiter, routes)` → 404 → `errorHandler` (must stay last). Inside `routes/index.js`: `/auth` first, then `router.use(auth)` and `router.use(requirePasswordChanged)` — **every other `/api/v1` route requires a valid token of an active user with no pending forced password change**, including all GETs and unknown paths (401 / 403 before 404). `server.js` validates env and connects to Mongo **before** `listen`.

Layering, one file per domain in each folder:
`routes/<domain>.routes.js` → `controllers/<domain>.controller.js` → `services/<domain>.service.js` → `models/<entity>.model.js`, with `validators/<domain>.validator.js` (Joi).

Conventions to follow when adding endpoints:
- Mount new routers in `src/routes/index.js`; never register API routes on `app` directly.
- Route order: `requirePermission('name'), <project-access check>, validate(schema), controller.fn` — `auth` is applied once in `routes/index.js`, don't repeat it. Routes name a permission, never a role list (D66b, `middlewares/auth.js`; an unknown name throws when the routes load). A GET with no `requirePermission` is open to every signed-in role, viewer included. `tests/permissions.test.js` fails if a write route has no permission or a module outside `config/` uses the role groups.
- **Project access (D66a)**: every project-scoped route has one check from `middlewares/projectAccess.js`, which calls `services/access.service.js` (`assertProjectAccess(user, projectId)` → 404, not 403; `projectFilterFor(user)` → a `Project` filter): `fromParam('id'|'projectId')`, `fromBody('project')` (POST screenings/assessments, after `validate`), `fromRecord(Model, param, notFoundMessage)` for routes by a record's own id (screening, assessment, monitoring record, file: loads its project first; after `validate`, so an invalid body stays 400), `list()` for `GET /projects` and `GET /dashboard` (sets `req.projectFilter`, which the service ANDs into its query). In v2 both allow everything (no visible change); v3 adds membership there. Only `POST /projects` is exempt; `/library` is organisation data, not project-scoped (no check). A new project-scoped route must use one; `tests/projectAccess.test.js` checks the route table (every prefix classified) and stubs a denial (404, nothing written) on every route.
- `validate(schema)` checks **`req.body`** (`validate(schema, "query")` checks `req.query`; `abortEarly:false, stripUnknown:true`) and **replaces it with the stripped value** (defaults applied, types converted): a field not in the schema never reaches the controller. Keep server-owned fields (`status`, `officer`, `approved_by`, `reject_by`, `reject_reason`, `recommendations` — the approver's field, set only by `PATCH …/approve` (D63 a) — totals, `is_active`) out of the schemas.
- Updates of a screening or assessment call `assertSameProject` (`src/utils/assertSameProject.js`): changing `project` → 400. Tools 3–5 are written only through the bulk saves, which take the project from the URL (a `project` in a row is stripped).
- Auth errors: bad/expired/forged token, unknown or inactive user → 401; wrong role → 403 `Forbidden`; pending forced password change → 403 with `code: "PASSWORD_CHANGE_REQUIRED"`; unexpected verify error → 500 `Server Error` (no stack, no details). An `ApiError` with a string `code` property adds `code` to the error response.
- Controllers are wrapped in `asyncHandler` and respond `{ success: true, data }`; errors are thrown as `new ApiError(status, msg)` (`src/utils/ApiError.js`) and become `{ success: false, error }`. Mongoose CastError → 404, duplicate key → 409.
- Models use snake_case fields, `timestamps: true`, `versionKey: false`. References use `ObjectId` + `ref`.

Roles (`src/config/roles.js`): `admin`, `environmental_specialist`, `program_manager`, `project_manager`, `environmental_focal_point`, `viewer`.
- Role groups (`config/roles.js`, used only by `config/permissions.js`): editors (all but viewer): create/update and submit. Specialists (`admin` + `environmental_specialist`): approve/reject screening & assessment, delete/archive/restore project. Library managers (`LIBRARY_MANAGER_ROLES`, today `admin` + `environmental_specialist`, its own list on purpose): manage the reference library (D64). Admin: manage users (D21), purge archived projects, read the audit log. Viewers read only. There is no per-project access rule yet (the D66a check allows everyone).
- Inactive users (`is_active: false`): login → 403 `Account is deactivated` (only after a correct password); existing tokens → 401 on the next request.
- Users (D21–D23, phase 6): `GET /users` — admin: every account incl. inactive (job_title populated); other roles: active users only with `_id, name, job_title, is_active` (pickers, D4). Admin only: `POST /users` (`name, email, role, job_title`; no password — the server generates a 12-char temporary password, returned once as `temporary_password`, and sets `must_change_password`; duplicate email → 409), `PUT /users/:id` (`name, role, job_title`; email is fixed; `job_title: null` clears; unknown job title → 400), `PATCH /users/:id/deactivate|reactivate`, `POST /users/:id/reset-password` (new temporary password, `must_change_password`). The last **active** admin can be neither deactivated nor given another role → 409. `POST /auth/register` is gone.
- Own password: `PUT /auth/password` `{ current_password, new_password }` (any role) → same shape as `/auth/me`, clears `must_change_password`. Wrong current password → 400 (not 401), same password → 400. Policy: `PASSWORD_MIN_LENGTH` (6) in `validators/auth.validator.js` — security, so D57 does not remove it; login only requires a value. While `must_change_password` is set, only `GET /auth/me` and `PUT /auth/password` answer (logout is client-side; there is no endpoint).
- Permissions (D35, D66b, `src/config/permissions.js` — the only role → permission map): `can(user, name)` and `permissionsFor(user)` take the user. `PERMISSIONS` = the general permissions (each a role group); `ACTION_PERMISSIONS` = the names routes and `allowed_actions` use (`project.create|edit|delete|archive|restore|purge`, `screening.*` / `assessment.*` `create|edit|submit|approve|reject`, `semp.edit`, `monitoring.edit`, `files.edit`), each granted by one general permission. `GET /auth/me` → `{ user (job_title populated, must_change_password), permissions, password_rules: { min_length }, upload_rules: { max_bytes, extensions, library_extensions } }` — `create_project`, `edit`, `export` (editors; never viewer, D28a), `approve`, `delete_project`, `archive_project` (specialist/admin), `manage_library` (library managers), `manage_users`, `purge_project`, `read_audit_log` (admin). Project-level `allowed_actions` (below) add the workflow state on top.

Rate limits: 1000 req / 7 min on `/api/v1`, keyed per user id when the token is valid, per IP otherwise; login 10 failed attempts / 15 min per IP.

Each project has at most one screening and one assessment (unique indexes; a second create → 409), one score per (assessment, question) and one monitoring record per (project, indicator). `GET /<domain>/project/:projectId` answers "not started yet" with **`200 { data: null }`** (screening, assessment) or `200 { data: [] }` (management, mitigation, monitoring) — never 404 (D34). Services populate user refs (`officer`, `approved_by`, `reject_by`, `responsible`) with `job_title`; `officer` is set on create and on submit.

Statuses for screening & assessment: `draft | submitted | approved | rejected`, changed **only** through `PATCH /<screenings|assessments>/:id/submit|approve|reject` (`src/utils/statusTransition.js`): `draft|rejected → submitted` (editors; sets `officer`), `submitted → approved|rejected` (specialist/admin; sets `approved_by` or `reject_by` + `reject_reason`; a specialist may approve their own work). Any other transition → 409. `status` in a create/PUT body is ignored. Each create and transition appends `{ status: created|submitted|approved|rejected, by, at, note? }` to `status_history` (note = reject reason), returned with `by` populated (`name`, `role`).

Impact levels everywhere: `negligible | low | medium | high | not_applicable`. Screening category codes: `A`–`F`.

### Workflow state & aggregate endpoints (D30–D32, D35)

`computeWorkflow()` in `src/services/workflow.service.js` is the one source of truth for project state; the gates below use it too. Per step (`screening`, `assessment`, `semp`, `monitoring`) a status `locked | not_started | in_progress | submitted | approved | rejected | completed` (screening/assessment `draft` → `in_progress`); plus overall `status` (`draft | in_progress | needs_action | monitoring | completed`), `current_step`, `percent_complete` (approved/completed = 1 step, in_progress/submitted/rejected = ½, of 4), `next_action` (`step`, `tool`, `route` = frontend `ROUTES` key, `label`, `description`), SEMP `management_activities` / `mitigation_plans` `{ count, described, status: not_started|in_progress|completed }`, monitoring `records`/`complete_records`/`quarters_filled` (monitoring is in progress once it has any record, a baseline alone included, and completed once one record has all four quarters). `loadWorkflowInputs(ids)` loads many projects in 5 queries — never loop per project. `allowedActions(user, project, workflow)` (the user's permission of the same name + the workflow condition) → e.g. `project.edit|archive|restore|delete|purge`, `screening.create|edit|submit|approve|reject`, same for `assessment`, `semp.edit`, `monitoring.edit`, `files.edit` (editors, no workflow lock), `export` (archived: only restore/delete/purge/export).
- `GET /dashboard` → `{ stats: { total_projects, by_status, high_risk (category A/B) }, latest_projects (5, newest update first) }`, archived left out.
- `GET /projects` → each project + `screening`/`assessment` summary (or null) + `workflow` + `allowed_actions`, and `pagination: { page, limit, total, pages }` next to `data`. Query: `archived`, `search` (title/location), `status`, `category`, `sort` (`createdAt` default, newest first | `updatedAt` | `title` | `start_date`), `page`, `limit` (≤ 100; **no `limit` = all**, as the current frontend expects). Invalid values → 400.
- `GET /projects/:id/workspace` → `{ project (archived_by populated), workflow, allowed_actions, screening, assessment, counts }` — works on archived projects. `GET /projects/:id` (plain project) is kept but the frontend doesn't use it.
- `GET /lookups` → `{ impact_categories, impact_questions, indicators, job_titles, places, place_groups }` (the only lookup endpoint).
- **Places (D64 a)** — `config/places.js`, a code registry of where library guidance can appear: each `{ key, label, group, scope, locked }`; groups `project_workflow` (`screening`, `assessment`, `management` = Tool 3, `mitigation` = Tool 4, `monitoring`), `project_support` (`semp_plan`, `stakeholder_awareness`, locked = v3), `organization` (`ghg_emissions`, `environmental_data`, locked, scope `organization`). Keys are stable and never tool numbers. The frontend keeps no copy (it reads `/lookups`). A new tool = one entry here + `handle: { place }` on its route (frontend).
- **Reference library (D64 b; `LibraryDocument` model, `services/library.service.js`, `routes/library.routes.js`)**: organisation guidance, not tied to a project. `title`, `description`, `places` (place keys, may be empty = general), `order`, one **PDF only** (extension + first bytes), stored at `<UPLOADS_DIR>/library/<uuid>.pdf`, same size limit, `uploaded_by` (creator), `updated_by`. `GET /library` (all roles; `?place=`, `?search=` title/description; sorted `order`, then title), `GET /library/:id/file` (all roles, same headers as project downloads). `manage_library` only: `POST /library` (multipart `file` + `title`, `description`, `places` as `a,b` or the field repeated, `order`), `PATCH /library/:id` (`title|description|places|order`, at least one), `PUT /library/:id/file` (new PDF, links and title kept; the old file is removed after the row points to the new one), `DELETE /library/:id`. Unknown place → 400; locked places accepted. Logged: `library.replace_file`, `library.delete`; create/edit are not.
- **File storage (one helper)**: `services/fileStorage.service.js` checks every upload (`checkUpload(file, allowedExtensions)` → extension, first bytes, empty, cleaned display name), writes it under a server-generated name (`store(folder, …)`, folder = project id or `library`), resolves paths inside `UPLOADS_DIR` only (`storedPath`/`readablePath`), removes files without throwing, and sends downloads (`send`). Project documents and the library both use it; nothing else touches the uploads folder.
- Bulk saves (editors; the only writes of Tools 3–5, gated like the other tools): `PUT /projects/:id/management` and `/mitigation` with `{ rows }` replace the whole table — a row with `_id` updates that row (fields not sent keep their value), a row without one is created, rows left out are deleted, a row without `serial_number` gets its position. `PUT /projects/:id/monitoring` with `{ records }` upserts by `indicator` (must exist, once per payload); records not sent stay. Every row is checked first (Joi, responsible rule, ids of this project, model validation → 400 `Row n: …` / `Record n: …`) and nothing is written on error; the writes then go out as one `bulkWrite` (no transaction: the local MongoDB is standalone; phase 11 adds a single-node replica set and a transaction). Responses return the saved table/records like the `GET …/project/:projectId` endpoints.
- Project documents (D47, D64 d; `ProjectFile` model, `config/files.js`, `services/projectFile.service.js`): `GET /projects/:id/files?area=documents` (default area; all roles, oldest first, `uploaded_by` populated), `POST /projects/:id/files` (editors; multipart `file` + `area` + `category` — documents: a project-workflow place key or `other`, required; old `annex`/`annex_*` values → 400), `GET /files/:fileId/download` (all roles; `Content-Disposition` with the UTF-8 name, `Cache-Control: private, no-store`), `DELETE /files/:fileId` (editors), `PATCH /files/:fileId` (`category`, `semp_record` files only). Allowed: PDF + Office (`pdf doc docx xls xlsx ppt pptx odt ods odp`, owner) — checked by extension **and** first bytes; the stored MIME type comes from the extension, never the client. One file per request, parsed in memory by `multer` 2 (`middlewares/upload.js`) → too big 413, wrong type/content, empty, no file, bad category → 400; nothing is written on error. Stored at `<UPLOADS_DIR>/<project id>/<uuid>.<ext>`; the client name is display only (last path segment, no control chars, ≤ 200). Archived project → 409 on upload/delete; reads stay. Area `semp_record` (SEMP Plan §7, 11 categories or `null`) exists in the model but answers **404** everywhere until v3 (`OPEN_AREAS` in `config/files.js`, a code constant — D48). `removeProjectData` (delete, purge, demo reset) removes the project's file rows and folder last; disk failures are logged, never thrown. Deleting a file is logged (`file.delete`, D65).
- Removed in phase 5 (unused by the frontend, `tests/removedEndpoints.test.js`): `GET /screenings`, `/assessments`, `/monitoring` (lists), `GET /lookups/<one>`, row writes `POST/PUT/DELETE /management|mitigation[/:id]`, `POST/PUT /monitoring[/:id]`, `PATCH /monitoring/:id/quarter/:q`, `POST /assessments/:id/methods|consultations` (the PUT replaces the list), `PATCH /assessments/:id/calculate` (totals are recalculated on every score change). GET-by-id reads stay. Removed in phase 8 (D63 c): `GET /assessments/:id/methods|consultations|scores` — `GET /assessments/project/:projectId` (and the create response) embed `methods`, `consultations` and `scores` in the assessment, so Tool 2 is read in one request.

### Workflow rules (`src/services/workflow.service.js`)

Every create/update/delete of project data calls a gate; reads never do. **Every broken workflow rule is 409** (gate, lock, archived, duplicate):
- **Order** (any screening category A–F, E included): assessment and its children need the screening approved (`requireScreeningApproved`); management activities and mitigation plan need the assessment approved (`requireAssessmentApproved`); monitoring needs Tools 3 and 4 complete — at least one row each, every row with its description (`requireSempComplete`).
- **Archive**: `PATCH /projects/:id/archive|restore` (specialist/admin) sets `archived` + `archived_by`/`archived_at`. Archived projects are hidden from `GET /projects` (`?archived=true` lists only them), still readable by id, and every write on them (project PUT, all tools, transitions) → 409 (`assertProjectWritable`, called by all gates). `DELETE /projects/:id` → 409 when the screening or assessment is approved (archive instead); otherwise it deletes the project with all its data. `DELETE /projects/:id/purge` (**admin only**, D60) permanently deletes an **archived** project, approved work included (not archived → 409), after writing its audit entry (`project.purge`, required: if the entry cannot be written, nothing is purged).
- **Critical-actions log (D65)**: `models/auditLog.model.js` + `services/audit.service.js` — `record(user, action, { project, target: { type, id, label }, snapshot, details })` is the only writer (a test fails if another module loads the model). Entry: `action`, `by` + copied `by_name`/`by_role`, `project` + copied `project_title`, `target_type`/`target_id`/`target_label`, `snapshot` (the record as it was), `details`, `createdAt`. Written after the action succeeded; a failed write is logged with `console.error` and the request still answers (phase 11: transaction). Keys matching password/token/hash/secret are dropped. Logged (exactly): `project.delete` (snapshot: title, location, statuses, row and file counts), `project.purge` (same + archive info), `project.archive|restore`, `file.delete` (name, area, category, size, uploader, date), `library.replace_file` (`snapshot`: title, `old_name`, `old_size`; `details`: `new_name`, `new_size`), `library.delete` (title, description, places, order, name, size, uploader, date; target type `library_document`, no project), `management.rows_removed` / `mitigation.rows_removed` (only when a bulk save deletes rows: `snapshot.rows` = `{ _id, serial_number, description }`, `details.removed`), `user.create` (name, email, role), `user.role_change` (only when the role changes: `details.from/to`), `user.deactivate|reactivate|reset_password` (name, email). Not logged: creates, edits, submit/approve/reject (`status_history`), uploads (`uploaded_by`), sign-ins, CLI scripts. `GET /audit-logs` (`requirePermission('read_audit_log')`, admin): newest first, `page`, `limit` (≤ 100, default 50), `action` (an action or a prefix such as `user.`), `from`/`to` (ISO, inclusive) → `{ data, pagination }`; invalid → 400. No endpoint writes, edits or deletes entries. A phase that adds a critical action logs it here and tests the entry (README rule).
- **Locking**: screening/assessment PUT and assessment methods/consultations/scores/calculate only while `draft` or `rejected` (`assertEditable` in `utils/statusTransition.js`); `submitted`/`approved` → 409. No reopen. SEMP, monitoring and project metadata stay editable (unless archived).
- **Assessment create** prefills empty `project_activity` (← project `project_component`, 400 if neither) and `potential_negative_impact`/`potential_positive_impact` (← screening), once; and creates one `negligible` score per `ImpactQuestion`. `POST /assessments/:id/scores` upserts only the questions sent (others keep their level; duplicate or unknown question → 400) and returns all scores. `total_project_score` counts and `total_project_impact` (highest level: high > medium > low > negligible > not_applicable) are recalculated on every score change; `PATCH .../calculate` is kept but optional. Submit → 400 unless every question has a score.
- **Responsible** (Tools 3, 4, 5): `responsible` (user id) **or** `responsible_text` (external party), never both (400). Setting one clears the other (`utils/responsible.js`). Frontend: `components/semp/ResponsibleSelect` has an "Internal user / External party" switch (user picker or free text); switching clears the other value; `onChange({ responsible, responsible_text })`.
- No minimum-length rules anywhere (D57); monitoring quarter values and `total` are free text, never parsed.

## Frontend architecture

- Entry: `index.html` (inline script applies saved theme from `localStorage['esms-theme']`) → `src/main.jsx` providers: `QueryClientProvider` (`services/queryClient.js`) → `AuthProvider` → `ThemeProvider` → `ToastProvider` → `App` (`ErrorBoundary` + `OfflineBanner` + `RouterProvider`).
- Path alias `@` → `src/`. Barrels (`index.js`) in components/hooks/services/contexts/utils — import from them.
- **All HTTP goes through `src/services/api.js`** (axios instance: attaches `Bearer` token from `localStorage['token']`; on 401 clears auth and hard-redirects to `/login`; on 403 `PASSWORD_CHANGE_REQUIRED` hard-redirects to `/change-password`). `extractErrorMessage` turns a wrong-role 403 (`Forbidden`) into a friendly message and keeps other 403 reasons (e.g. `Account is deactivated`). Use `extractErrorMessage(err)` for user-facing errors. Never call `fetch`/raw axios to the API.
- Layering: `services/<domain>Service.js` (thin API calls) → `hooks/use<Domain>.js` (TanStack Query: `useQuery` for reads, `useMutation` for writes; returns loading/error/data + actions) → `pages/` and feature `components/<domain>/`. No global store; the query cache is the shared state, plus Auth/Theme contexts. Every query key comes from `services/queryKeys.js` (`['me']`, `['lookups']`, `['users']`, `['dashboard']`, `['projects']`, `['workspace', id]`, `['screening'|'assessment'|'management'|'mitigation'|'monitoring', id]`, `['files', id, area]`, `['library', place|'all']`, `['audit-logs', params]`). Defaults: `staleTime` 30 s, no refetch on focus, no retry on 4xx.
- Reads: `useDashboard` (`GET /dashboard`), `useProjects` (`GET /projects`, + `deleteProject`), `useWorkspace(projectId)` (`GET /projects/:id/workspace`: project, `workflow`, `allowed_actions` as `can(action)`, summaries, counts), `useLookups` / `useUsers` (`GET /lookups`, `GET /users`, loaded once, only where used). Guards, `ProjectLayout`, sidebars and pages share the workspace query; `ProjectLayout` passes `{ project, workflow, counts, can }` as outlet context (`useProjectContext()`). The dashboard loads in 2 requests (`/auth/me`, `/dashboard`), a project overview in 2 (`/auth/me`, workspace), the assessment pages make one assessment request (`useAssessment` reads `GET /assessments/project/:id` only; no `/lookups` unless the page uses `useLookups`); a tool page adds at most one `/library?place=` request (none when cached) — `src/routes/requestCounts.test.jsx` asserts it.
- Writes: tool hooks write through `useProjectSave(projectId)` — one mutation, its result put into the tool's query, then `invalidateProjectState()` (workspace refetched before the save resolves, project list and dashboard marked stale). A new write in a tool hook must go through it. Tools 3/4 (`useManagementActivities`, `useMitigationPlans` in `hooks/useSemp.js`) and Monitoring (`useMonitoring`) keep edits local and save with ONE bulk request per Save (D32); `utils/responsible.js` always sends `responsible` + `responsible_text`.
- Routing: `src/routes/index.jsx` (all pages lazy-loaded) + `routes.config.js` (`ROUTES` constants, `getProjectRoute(id, ROUTES.X)`, sidebar nav config). Use `ROUTES` constants rather than hardcoded paths.
- Workflow state comes only from the backend (D30): read `workflow.steps.<step>.status`, `workflow.status`, `percent_complete`, `next_action` (helpers in `utils/workflowSteps.js`). No workflow rule or role list lives in the frontend. Gates are enforced by the backend (409, shown through `extractErrorMessage`); `WorkflowRouteGuard step="assessment|semp|monitoring"` redirects a `locked` step to the open step before it. `SettingsRouteGuard` = `canAccessSettings` (`manage_users` or `delete_project`); Settings shows Users only with `manage_users` (admin) and Projects only with `delete_project`. Settings → Activity log (`ROUTES.SETTINGS_ACTIVITY_LOG`, `pages/settings/ActivityLogPage` + `components/settings/ActivityLogSection`, data via `hooks/useAuditLogs`, key `queryKeys.auditLogs(params)`) is behind `PermissionRouteGuard permission="read_audit_log"` (others → Settings); `SettingsNav` shows the tabs the user may open. Action labels, filter groups and snapshot formatting live only in `utils/auditLabels.js`.
- Permissions (D35): `useAuth()` loads `GET /auth/me` once per session (`isLoading` until then) — `can(permission)` plus `canCreateProject`, `canEdit`, `canExport`, `canApprove`, `canManageUsers`, `canDeleteProject`, `canReadAuditLog`, `canAccessSettings`, plus `mustChangePassword`, `passwordRules` and `changePassword()`; logout clears the query cache. `ProtectedRoute` sends a user with `must_change_password` to `ROUTES.CHANGE_PASSWORD` (`pages/auth/ChangePasswordPage`, forced change, D22); `ROUTES.PROFILE` (`pages/profile/ProfilePage`) holds the own-password form (`components/auth/ChangePasswordForm`, D23), reachable from the user menu. Settings → Users (`components/settings/UsersManagementSection` + `UserFormModal` / `TemporaryPasswordModal`, writes via `hooks/useUserManagement`) is the admin user lifecycle; Responsible pickers get `useUsers().activeUsers`, and a row whose responsible user was deactivated still shows the name as `(inactive)`. On a project, use the workspace's allowed actions instead (`can('screening.approve')`, `can('semp.edit')`, `can('export')` …): they also cover the workflow state and archived projects. Export buttons only with `export` (viewers never, D28a). Screening/assessment are submitted with `screeningService.submit` / `assessmentService.submit` (save first, then the transition endpoint); never send `status` in a create/PUT.
- Project documents (D64 d): `ROUTES.PROJECT_DOCUMENTS` (project nav "Documents"), `pages/project-workspace/documents/ProjectDocumentsPage` + `components/documents/DocumentSection`: one section per project-workflow place (labels from `useLookups().placesByGroup`), then "Other". Data via `hooks/useProjectFiles` (`services/fileService.js`, key `queryKeys.files(projectId, area)`). Files don't change workflow state, so its writes refresh only that list, not through `useProjectSave`. Uploads go one file at a time, then one refresh; files are pre-checked with `useAuth().uploadRules` (`utils/fileRules.js`). PDFs open in the `PdfViewer`, Office files download only. Upload/delete only with `can('files.edit')`.
- **PdfViewer** (`components/files/PdfViewer.jsx`, shared): mount it only while open; it fetches the PDF as a blob with the token (`load()` → `fileService.download` / `libraryService.download`, both via `getBlob`), shows it in an `iframe` on a `blob:` URL, revokes the URL on close, has a Download button, and shows "Download to view" where `navigator.pdfViewerEnabled === false`. Overlays (`ui/SidePanel`, the viewer) use `ui/useOverlay`: Escape closes only the topmost, the page behind stays mounted (unsaved input kept). Confirmations: `components/files/ConfirmDeleteModal`. Downloads: `utils/saveBlob.js`.
- **Library (D64 b, c)**: `ROUTES.LIBRARY` (main nav + mobile menu), `pages/library/LibraryPage`: one `useLibrary()` request, search and place filter (incl. "General — Library only") client-side; with `canManageLibrary` (`manage_library`) upload/edit (`components/library/LibraryDocumentFormModal` + `PlacePicker`: places grouped by group, v3 places tagged and selectable), replace PDF, delete (in-app confirm); writes via `useLibraryManagement()` refresh `['library']`. **Guidance button**: a route with `handle: { place }` (`routes/index.jsx`: screening, assessment, Tool 3 `management`, Tool 4 `mitigation`, monitoring) gets `components/library/GuidanceButton` in the layout header (`ProjectLayout`, `SempFullWidthLayout`, via `useCurrentPlace()`): "Guidance (n)" from `useLibrary({ place })` (`queryKeys.library(place)`, 5 min stale), hidden at n = 0; it opens a side panel, a document opens in the `PdfViewer`. Activity-log labels for places come from `/lookups` (`describeAuditEntry(entry, { placeLabel })`); old `annex`/`annex_*` entries read "(before phase 7b)".
- Excel export is fully client-side (`utils/excelExport/`, loaded with `await import('@/utils/excelExport')`; ExcelJS in the `vendor-excel` chunk, ~930 kB, the only chunk allowed over 500 kB — `warnLargeChunks` in `vite.config.js`). All five tools reproduce the official AKF workbook sheets ("Tool 1" … "Tool 5", D52, D67 a): one builder per sheet (`tool1Sheet`, `tool2Sheet`, `tool34Sheets`, `tool5Sheet`) that adds its sheet to a given workbook; shared cell helpers in `sheetKit.js` (Arabic text → `readingOrder: 'rtl'`), status/file name/footer in `exportMeta.js`. `exportTool(tool, data, exportStatus(workflow, tool, record))` saves one tool; `exportProjectWorkbook(data)` (via `hooks/useProjectWorkbook`, the overview's `ProjectWorkbookCard`, only with `can('export')`) saves one file with a sheet per tool that has data, Tool 1 → Tool 5 (D67 b), loading only what those sheets need. Every export carries the tool status (from `workflow.steps`: Draft/Submitted/Approved/Rejected, In progress/Completed) and the date in the file name (`Tool2_<project>_Draft_2026-11-04.xlsx`, `ESMS_<project>_<date>.xlsx`) and in the printed page footer, never in the sheet area (D67 d). Layout headers trigger exports via window events: `screening-export`, `assessment-export`, `semp-export` (`detail.toolType: 'tool3'|'tool4'`), `monitoring-export`. ### Styling rules (from `frontend/docs/STYLE_GUIDE.md` — mandatory)

- Use design tokens only: `bg-background`/`dark:bg-background-dark`, `bg-surface`/`dark:bg-surface-dark`, `text-text-main`/`dark:text-white`, `text-text-secondary`/`dark:text-gray-400`, `border-border-default`/`dark:border-border-dark`, `text-primary`, `bg-primary-soft`, `border-primary-border`, `bg-card-dark`, the AKF `green-50…950` scale (D49, primary `#008c54`). Tokens are defined in `src/index.css`.
- Forbidden: `dark:bg-gray-800/900/700`, `border-gray-200`, `dark:border-gray-700`, `bg-gray-100`, arbitrary hex like `bg-[#1a1a1a]` / `text-[#888]`.
- Merge classes with `cn()` from `@/utils/cn`. Reuse `@/components/ui` (Button, Card with `Card.Header/Body/Footer`, Input, Modal, Toast, …) instead of new primitives.
- Icons: Material Symbols only (`<span className="material-symbols-outlined">name</span>`).
- Every UI change must work in both light and dark mode.
- Prettier: no semicolons, single quotes, 2 spaces, width 100, trailing commas es5, LF.
